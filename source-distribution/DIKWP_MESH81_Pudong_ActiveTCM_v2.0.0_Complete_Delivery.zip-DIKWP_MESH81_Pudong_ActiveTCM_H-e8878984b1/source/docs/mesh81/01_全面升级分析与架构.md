# 全面升级分析与目标架构

## 1. 原项目价值

原项目已经建立了一个较完整的中医主动健康工作流原型：28 个优势病种工作流容器、5 个院本能力扩展包、主动采集、四诊表达账本、多病种并行路径、人工诊疗方案、康复与随访、转诊、FHIR 导出、乐观并发控制和哈希审计链。其最重要的工程价值并非“替代医院系统”，而是把中医连续照护中的意图、观察、路径、人工决策、康复任务、转诊和残差形成可检查的数据结构。

## 2. 原项目进入医院环境前的主要缺口

| 维度 | 原型状态 | 生产缺口 | 本次升级 |
|---|---|---|---|
| 接口 | 单一 REST 与 FHIR 导出 | 缺少双向、传统协议和厂商适配 | FHIR、HL7 v2、CDA、DICOMweb、REST、Webhook、文件交换 |
| 主索引 | 病例内部标识 | 多系统患者号冲突、重复和误并风险 | 保守 MPI、候选匹配、人工链接、标识掩码 |
| 身份 | 演示账号/令牌 | 未接统一身份、组织和真实角色 | 可信代理、签名令牌、IdP 连接模板、角色映射 |
| 可靠性 | 直接同步调用 | 超时、重复、乱序、对方停机 | 幂等、租约、重试、死信、重放、连接器健康 |
| 签名/同意 | 演示角色标签 | 无真实签名、用途和授权证明 | 同意记录、用途门、摘要签名信封、外部平台适配 |
| 临床安全 | 人员在环 | 外部数据直接写入可能绕过复核 | 暂存—审核—批准/驳回桥接；高影响写回默认禁用 |
| 可观测性 | 应用审计 | 缺接口级指标、队列和协议追踪 | 控制台、健康检查、指标、审计链、请求 ID |
| 数据治理 | 病例 JSON | 映射版本、来源、残差不充分 | 规范信封、映射版本、原始摘要、语义护照 |
| 部署 | 本地 Python/Docker | 缺院内部署、备份、容灾模板 | Docker、Nginx、systemd、K8s、备份恢复和上线清单 |

## 3. 目标架构

```text
患者端/医护端/原临床工作台
              │
              ▼
┌──────────────────────────────────────────────┐
│ 原 ActiveTCM 临床工作流内核（8788）          │
│ 主动采集｜四诊账本｜路径｜人工方案｜康复｜转诊 │
└──────────────────────────────────────────────┘
              ▲ 仅经审核桥接
              │
┌──────────────────────────────────────────────┐
│ MESH8.1 院内集成网关（8790）                 │
│ 规范信封｜D/I/K/W/P 语义护照｜字段映射        │
│ MPI｜同意｜签名信封｜暂存审批｜审计链          │
│ 可靠队列｜重试｜死信｜连接器健康｜运维控制台   │
└──────────────────────────────────────────────┘
   ▲             ▲              ▲             ▲
   │ FHIR/HL7    │ CDA/DICOMweb │ REST/Webhook│ 文件/MFT
   │             │              │             │
 HIS/EMR       LIS/RIS/PACS     IdP/电子签名   区域平台/厂商系统
```

### 3.1 解耦原则

临床内核不直接持有每一家厂商的连接参数；集成网关不直接形成临床结论。这样可以：

- 更换 HIS/LIS/PACS 厂商时只替换连接器和映射；
- 接口故障时不破坏临床病例主数据；
- 使映射残差、身份不确定性和权限不足显式存在；
- 将生产写回控制在医院现有授权、签名和责任链内；
- 对每次转换和人工批准进行独立审计。

## 4. MESH8.1 语义护照

每条入站/出站消息都可附带五个显式位置：

- D（同）：哪些标识、字段和关系被声明为保持同一；
- I（异）：哪些值、版本、单位、代码或观察者不同；
- K（整）：当前任务下形成了怎样的完整上下文；
- W（值）：用途限制、最小必要、临床安全、数据质量和伦理约束；
- P（意）：为何接收、转换、暂存、查询或发送，以及允许的输出动作。

语义护照不是一个可抵消风险的总分。缺失身份、目的、权限或人工复核时，不允许用“总体置信度较高”掩盖该缺口。未给出的内容保持未给出；映射无法表达的内容进入残差账本。

## 5. 接口分层

### 5.1 传输层

HTTPS/mTLS、MLLP、院方 MFT/SFTP 挂载目录、反向代理、消息总线适配点。

### 5.2 协议层

FHIR R4、HL7 v2 ER7、CDA R2、DICOMweb、REST/JSON、JSONL/CSV。

### 5.3 规范模型层

患者、就诊、观察、报告、文档、预约、任务、服务请求、用药请求、影像目录、同意、来源和审计等资源。

### 5.4 语义与治理层

字段映射、代码映射、单位处理、身份匹配、目的限制、权限、同意、签名、残差和版本追溯。

### 5.5 临床桥接层

所有高影响信息先暂存；持有相应角色的人员核对来源、患者、就诊、时间、单位、状态和用途后批准或驳回。批准并不等于自动形成诊断、处方或医嘱。

## 6. 数据流示例

### 6.1 LIS 检验结果

1. LIS 发送 ORU^R01；
2. HL7 解析器校验 MSH/PID/OBR/OBX；
3. MPI 用患者号等标识解析患者；
4. 映射为 Observation/DiagnosticReport 暂存资源；
5. 保存原始消息摘要、消息控制号、映射版本和残差；
6. 生成 ACK；
7. 授权人员确认单位、参考范围、结果状态和患者归属；
8. 需要进入临床工作流时，经暂存桥接批准。

### 6.2 PACS 影像目录

1. 使用 QIDO 查询研究/序列/实例元数据；
2. 不默认下载像素数据；
3. WADO 查询由权限和目的控制；
4. STOW 默认关闭；
5. ImagingStudy/DiagnosticReport 只作为影像索引和报告关联，不替代影像诊断系统。

### 6.3 双向转诊

1. 临床人员在原系统形成转诊工单；
2. 集成网关生成出站规范信封；
3. 检查患者标识、目标机构、用途、同意和人工批准；
4. 通过区域平台 REST/FHIR/文件连接器发送；
5. 幂等键防止重复创建；
6. 失败进入重试或死信；
7. 对方回执更新工单状态，但不声称号源或床位已占用，除非真实接口明确返回并被院方确认。

## 7. 非功能目标

建议由院方在项目启动时把以下指标具体化：

- 可用性与恢复：RTO、RPO、备份频率、恢复演练；
- 性能：每类接口峰值 TPS、消息大小、P95/P99 延迟；
- 可靠性：幂等覆盖率、重试上限、死信处理时限；
- 安全：身份、最小权限、证书轮换、漏洞修复、审计留存；
- 数据：患者匹配准确性、字段完整率、代码映射覆盖率；
- 临床：人工复核时限、误关联零容忍、高影响动作双重确认；
- 运维：告警、容量、时间同步、日志接入、变更和回滚。

本发行包给出机制和模板，不替医院确定具体生产 SLA。
